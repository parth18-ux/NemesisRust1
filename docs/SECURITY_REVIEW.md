# Security review

A code review of the RuseTect server (`crates/rusetect-server`), the core library (`crates/rusetect`) and the website
(`service/static`), done on branch `ccr-a05856fa-mavodd` after the step 1 webhook changes. It complements
`docs/THREAT_MODEL.md` (STRIDE, per component) and does not replace it. **This is an internal review by the team that
wrote the code: there has been no external penetration test.** Every defect called fixed below has a test that fails
without the fix.

## 1. Auth and roles per route

Every `/api` request passes `require_key` (`crates/rusetect-server/src/lib.rs`), which applies one rule,
`rusetect::security::gate`:

* demo mode (`RUSETECT_DEMO=1`, no `RUSETECT_ANALYST_KEYS`) is open: the public demo needs that (section 12);
* otherwise a route in `PUBLIC_API` is open, anything else needs a known `X-Analyst-Key` (compared in constant time,
  `lookup`), and the role sets the reach: any role reads, a write needs `channel` or above, a review, triage, case or
  consortium publish needs `analyst` or `supervisor`, and `/v2/demo/*` needs `supervisor`. A write route not named in
  the rule falls to the channel rule, so a new route is never open to a viewer.

Handlers add their own checks on top (nonce, four-eyes, assignment rules, and `require_reader` on every read that names
accounts, which keeps those reads closed even if the gate were bypassed). The table below is **generated from the
code**: `crates/rusetect-server/tests/routes.rs` reads every `.route(...)` in `build_app`, runs it through `gate` once
per role outside demo mode, and fails when this table differs (`UPDATE_ROUTE_TABLE=1 cargo test --release --test
routes` rewrites it). The last column is hand-written in that test, and the test refuses a note for a route that does
not exist. `yes` means the gate lets the request through; `401` and `403` are the gate's answers; `open` marks pages and
static files, which need no key.

## 2. Input validation

* Bodies: capped at `MAX_BODY_BYTES` (2 MiB) by `DefaultBodyLimit`, answered `413` before a handler runs. JSON bodies are
  parsed by `parse_obj` with typed field readers (`crates/rusetect-server/src/validate.rs`, `inputs.rs`); a wrong type,
  a missing field or an out-of-range value is a `422` listing every bad field, never a panic. An error body is at most `MAX_ERROR_BYTES` (16 KiB); a longer one is clipped and marked
  `"truncated": true` (finding F7).
* Queries: integers through `int_query` (`422` when not a number). Paging is clamped: `/v2/transactions` at most 200 a
  page with a bounded offset; `/v2/graph` depth 1 to 3 and at most 300 accounts; `/v2/cases` and `/v2/alerts` take a
  bounded `limit`.
* Webhook: HMAC-SHA256 over `{timestamp}.{raw body}`, checked in constant time, 5 minute window, idempotent `event_id`
  (`docs/live.md`).
* Static files: `/assets/{*path}` serves only names in the embedded list (`ASSETS` in `lib.rs`); `..`, encoded `..` and
  unknown names are `404` (`tests/assets.rs`). Nothing is read from disk by a request-chosen path.
* State growth: accounts (`RUSETECT_MAX_ACCOUNTS`), typing profiles, the nonce cache, the rate limiter and the message
  log are all bounded. Stored alerts are not (`live:alerts` has no expiry), and every dashboard, transaction search,
  graph and alert-list request copies all of them (finding F5).

## 3. Secrets

* `check_config` fails closed: without `RUSETECT_ANALYST_KEYS` the server refuses to start unless `RUSETECT_DEMO=1`;
  with analyst keys it also requires the signing key, the consortium secret and the hash salt. Keys must be 16+
  characters; a bad key file is reported by entry position, never by key text (`parse_keys`).
* All secrets come from environment variables; none is in the repository. CI greps `service/static` for demo keys,
  private keys and cloud tokens (`.github/workflows/ci.yml`, "No secrets in the website's code").
* The website keeps the analyst key in `sessionStorage` (`assets/js/api.js`), so it is gone when the tab closes. That
  is why the pages' CSP (section 9) matters: script on this origin could read it.
* Residual: no key store or HSM, no expiry or per-key revocation, rotation is manual (`docs/RUNBOOK.md`).

## 4. Sensitive data in responses and logs

* A refused key is logged as `auth_failure_line`: method, path, client and the first 8 hex characters of the key's
  SHA-256, never the key (unit test `auth_failure_line_never_holds_the_key`).
* Message texts are redacted (`context_rules::redact`: phones, UPI ids, links and the like become placeholders) before
  they are stored or returned; `/v2/messages` returns only the redacted copy.
* `/v2/whoami` returns the analyst and role, never the key. `/v2/demo/analysts` returns keys only in demo mode, where
  they are the published demo keys, and `[]` otherwise.
* Errors are JSON `{"detail": ...}` with `X-Content-Type-Options: nosniff`. **Fixed (finding F1):** a failed read in
  `read_json` (behind `/v2/fixtures/mule`) answered with the absolute path of the file on the server; it now logs the
  path and answers only with the file name (test `read_json_failure_does_not_show_the_server_path`, `lib.rs`).
* Residual: a Redis failure on the webhook answers `503` with the Redis client's error text (`live.rs`, `unavailable`).
  The redis crate's URL errors are fixed strings (checked in its source), so the URL and password are not in it, but a
  connection error can name the host. Low.

## 5. The audit log

Every review, triage and case action is appended to a hash-chained log (`crates/rusetect/src/review.rs`);
`verify_chain` detects an edited entry, and `GET /v2/audit` returns the entries with `chain_valid`. Live decisions also
append to a hash-chained ledger, and assess results are signed with Ed25519 (`/v2/keys/public`, `/v2/verify`).
Residual: the chain is unsigned SHA-256 and not anchored outside the server, so someone who can write the store can
rewrite it and recompute every hash; with Redis, `allow` ledger entries are not chained (`docs/THREAT_MODEL.md`).

`cargo audit` (cargo-audit 0.23.0, RustSec database fetched on the day of this review) finds **no vulnerability** in
`Cargo.lock`, and CI fails the build on one. It reports two "unmaintained" warnings, accepted as exceptions:

## 7. Rate limiting

`rate_limit` counts every `/api/` request per client: `RUSETECT_RATE_LIMIT` requests per 10 s (default 240). The
client is the TCP peer, or the right-most `X-Forwarded-For` entry only behind a trusted proxy (`RUSETECT_TRUST_PROXY=1`
or Vercel), so a caller cannot pick a fresh identity per request (unit test
`client_key_takes_the_rightmost_forwarded_address_only_behind_a_trusted_proxy`). Residual: the counter is in memory per
instance, so several instances each count separately and a distributed flood is not limited; no WAF rule is set. The
webhook is not exempt, so a high-volume sender must raise the limit. The limit counts requests, not their cost: a
few dozen concurrent reads were enough to exhaust memory before the F5 fix (`docs/PERFORMANCE_REPORT.md`).

## 8. Single tenant

**RuseTect is single tenant.** One deployment serves one bank: one set of analyst keys, one store, one audit log. There
is no tenant id on any record and no isolation between two banks' data inside one process; running two banks on one
deployment would let each read the other's alerts. The "consortium" is a simulation inside one process: every member
bank and its key are created at start-up. Multi-tenancy would need a tenant on every key, record and Redis prefix, and
is not built.

## 9. Content security policy

| Page | Policy | Notes |
|---|---|---|
| `/app` | `APP_CSP` | Scripts and styles only from this origin, fonts from Google Fonts, `connect-src 'self'` |
| `/`, `/console`, `/investigate`, `/report` | `LEGACY_CSP` | Same, plus `style-src-attr 'unsafe-inline'` for the `style="..."` attributes the pages and their templates use |
| `/docs` | `DOCS_CSP` | Swagger UI from `cdn.jsdelivr.net`, pinned to 5.32.0 with subresource integrity |

All three set `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'` and `form-action 'self'`, and no
`script-src` contains `unsafe-*` (checked in `tests/assets.rs`). Every response also carries `X-Frame-Options: DENY`,
`X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.

**Fixed (finding F2):** the four older pages ran inline `<script>` and `<style>` blocks and were served with no CSP,
so an injected script would have run with access to the analyst key. Their code moved, unchanged, to
`service/static/assets/legacy/` (the landing page's colour tokens come from the shared `assets/tokens.css`), and they
are served with `LEGACY_CSP`. Tests: `tests/assets.rs` (header set, no inline `<script>` or `<style>`, every linked file
embedded) and `tests/e2e/smoke.js` ("legacy pages: CSP set, ...": each page draws, one action reaches the API, no CSP
violation or console error, at desktop, tablet and phone). Before and after were compared in Chromium: the computed
style of every element and full-page screenshots of `/` are identical at 1440, 834 and 390 px wide.

**Fixed (finding F3):** `/docs` loaded Swagger UI from the floating tag `swagger-ui-dist@5` with no integrity check, on
the origin that holds the analyst key, so any new release (or a compromised CDN) ran there. It is now pinned to 5.32.0
with `sha384` integrity on both files (hashes checked against the npm package), started from `/assets/js/docs.js`
instead of an inline script, with the validator badge (an image from swagger.io) turned off. Test: `tests/assets.rs`.

Residual: `style-src-attr 'unsafe-inline'` lets injected markup restyle a page (no script). Google Fonts is a
third-party origin for styles and fonts, without integrity (its CSS varies by browser).

## 10. XSS

The pages build HTML from API data with template strings. Every field a caller can set (account ids, banks, message
text, reasons, event ids, analyst names) passes through an escaping helper (`esc` in `assets/js/util.js` and in the
legacy scripts); ids the server mints (alert, case, campaign) are inserted as they are. API responses are JSON with
`nosniff`, so a response cannot be rendered as HTML. With the CSP of section 9, an injection that slipped past `esc`
could not run script on any page. Residual: the review of `innerHTML` call sites is by reading, not by a test of every
site.

## 11. Nonces

Every review, triage and case action needs a fresh `X-Nonce` (8 to 128 characters), remembered for 10 minutes
(`NonceCache`), so a captured request cannot be replayed. Keys travel in a header, not a cookie, so cross-site request
forgery does not apply. Residual: the cache is per instance, so with several instances a nonce could be replayed once on
another instance within the 10 minutes; review actions are still bound to the analyst's key and the alert's state.

## 12. Public demo exposure

The Vercel deployment runs in demo mode on purpose: the demo keys are published (`/api/v2/demo/analysts`), every route
is open, CORS is `*` unless `CORS_ORIGINS` is set, and anyone can reset the demo (refused with `409` once a live
decision is in the ledger) or play both analysts of a four-eyes block. It holds synthetic data only. **Never send real
data to it, and never set a webhook secret or Redis store with real payments on it**: the live feed would show them to
anyone. A pilot runs the binary inside the bank with keys set and no demo mode (`docs/PILOT.md`).

## 14. Review of 2026-11-23: external scanner follow-up

An external AI scanner (Hinoki) reported that `/api/health` on production shows an in-memory store, an ephemeral
signing key and demo keys, and that about 50 endpoints are exposed. This review checked that report against the code
and tested locally (`RUSETECT_DEMO=1`, release build). Production could not be probed from the review environment (its
network does not allow the host), so every production statement below is from the code plus the scanner's report.
Measured values are in `results/security_repro.json` (`tools/security_repro.py`, run on a local server before and after
the fixes).

### Production exposure

* **The scanner is right, and it is the configuration, not a bypass.** `"auth": "demo keys ..."` in `/api/health` means
  `RUSETECT_ANALYST_KEYS` is not set, so `KEYS.demo_mode` is true and `security::gate` lets every `/api` request through
  (section 1). `require_reader` and the handlers' `analyst_for` checks pass too, because the demo keys, including the
  supervisor key, are published at `/api/v2/demo/analysts`. An anonymous visitor can therefore read alerts, evidence
  packs, STR drafts, cases, the audit log and the consortium ledger; review and triage alerts (both analysts of a
  four-eyes block); open and close investigations; publish to the ledger as any member bank; register a duress PIN for
  any account id (first come, never overwritten); reset the instance's demo state; and run `/v2/payments/batch` and
  `/v2/demo/next`. All of it is synthetic data in one instance's memory, so confidentiality impact is low; integrity
  and availability of the public demo are not protected at all. Outside demo mode the gate and the route table of
  section 1 apply, and `check_config` refuses to start without the signing key, consortium secret and hash salt.
* **`/api/health`** shows the auth mode, the signing key id and whether it is ephemeral, the store kind and whether it
  is reachable, and the drift status. None of it is a secret (the key id is also at `/v2/keys/public`), and it is what
  the website's status chips and `tools/pilot_rehearsal.py` read. Accepted (Info). With Redis, `store.note` can hold a
  Redis client error; section 4 covers that text.
* **`api/rusetect.rs`** reads no secret itself: it runs the same `check_config`, `ensure_root` and `build_app` as the
  binary. The signing key, consortium secret and hash salt are read once at start-up from the environment; on Vercel
  `VERCEL` is set, so the rate limiter takes the client from the right-most `X-Forwarded-For` entry. State is per
  function instance and lost on a cold start, as the health report says.

### Parth actions (not changed by this review)

* **P1. Decide what the public site is.** If it stays a public demo, keep demo mode but treat it as untrusted and
  disposable (section 12). If it should be protected: in Vercel, Project, Settings, Deployment Protection, turn on
  Vercel Authentication (or Password Protection) for Production, so anonymous visitors cannot reach `/api` at all.
* **P2. To turn demo mode off on Vercel**, in Project, Settings, Environment Variables (Production): remove
  `RUSETECT_DEMO`; add `RUSETECT_ANALYST_KEYS` (JSON `{"<key of 16+ random characters>": {"analyst": "...", "role":
  "analyst|supervisor|viewer|channel"}}`), `RUSETECT_SIGNING_KEY` (`openssl rand -base64 32`),
  `RUSETECT_CONSORTIUM_SECRET` and `RUSETECT_HASH_SALT` (`openssl rand -hex 32` each); redeploy. The function refuses
  to start if one is missing (`check_config`), which is the check that it worked. The website then needs a key typed
  in; the public console stops working for anonymous visitors.
* **P3. For a demo that should survive cold starts**: set `RUSETECT_SIGNING_KEY` to a demo-only seed (signatures then
  verify across instances; never reuse it for a pilot), and connect a Redis store (Vercel Marketplace, Upstash), which
  sets `REDIS_URL`/`KV_URL`. Do not do this with real data on a demo deployment (section 12).
* **P4. Cost limits at the edge**: in Vercel, Project, Firewall, add rate-limit rules per IP, for example
  `POST /api/v2/payments/batch` 5 per minute, `POST /api/v2/demo/*` 30 per minute and `POST /api/v2/message`,
  `/api/v2/assess` 60 per minute; consider Attack Challenge Mode during abuse. This also covers the per-instance limit
  of section 7.
* **P5. CORS**: set `CORS_ORIGINS=https://nemesis-rust1.vercel.app` (Production) and redeploy.
