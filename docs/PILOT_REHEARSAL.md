# Shadow-pilot rehearsal

An end-to-end rehearsal of [PILOT_ONBOARDING.md](PILOT_ONBOARDING.md) on one machine, on **synthetic data only**: the
server in memory mode with analyst keys and throwaway secrets, the whole demo stream sent through the signed webhook by
`tools/pilot_sender.py`, sent again to check idempotency, then the fixed-budget evaluators of [PILOT.md](PILOT.md)
(`tools/pilot_freeze_policy.py`, `tools/pilot_evaluate.py`, `tools/pilot_queue.py`) run on the replay log. It checks
the plumbing a partner will use. It says nothing about accuracy on a bank's real payments, which is unverified.

Rerun: `cargo build --release -p rusetect-server --bin rusetect-server && python3 -I tools/pilot_rehearsal.py`. The
table is generated from [results/pilot_rehearsal.json](../results/pilot_rehearsal.json); the script's docstring
gives the fixture and label definitions.

## What worked

- **Signed ingest at volume.** Every event was accepted on the first attempt with no retry, the ledger chain verified,
  and `/api/v2/live` refused a request without an analyst key.
- **Idempotency** (after the fix below): the re-send of every event came back replayed with the same action and alert,
  and neither the alert count nor the ledger grew.
- **The evaluators run end to end on a sender log.** The policy was frozen on the validation days only, before any
  label was read, and the ranking and queue comparisons ran on the later days at the same daily budget, with the
  sender's `--log` as input and no hand editing.

## What broke, and what changed

1. **Memory mode forgot event ids and scored re-sends again (fixed).** The in-memory idempotency store kept the newest
   100,000 event ids and dropped the oldest. The first full rehearsal sent more events than that, so on the re-send the
   oldest ids were unknown, were scored again and evicted the next oldest in turn: no event of the re-send came back as
   replayed, the ledger doubled, and every payment was written into account history twice. The guide promised
   idempotency "for the life of the process". Now the store never forgets: once `RUSETECT_MAX_EVENTS` ids (default
   100,000) are stored, a new id is refused with `503` and nothing is committed, and known ids still replay. Test:
   `memory_mode_refuses_new_events_when_its_idempotency_store_is_full` in `crates/rusetect-server/tests/live.rs`. The
   rehearsal sets `RUSETECT_MAX_EVENTS` above the stream size, as the guide now tells a partner to (or to use Redis).
2. **The memory alert desk keeps 10,000 alerts** (`MAX_ALERTS` in `crates/rusetect/src/review.rs`): the table shows
   the alert count stopping there while far more payments were flagged; the oldest final, else oldest, alerts are
   dropped. Not changed (it is the documented memory bound), but a pilot that wants every alert kept should run with
   Redis ([live.md](live.md) section 6).
3. **The demo stream covers one calendar day**, while the evaluators freeze and measure in UTC days. The rehearsal
   re-dates each clock hour to its own day. That makes the gaps between hours a day long, which changes the engine's
   time-window features, so the comparison numbers above are a test of the tools, not of the engine.
4. **The queue tool asks for a `cascade` score the webhook does not return**; the rehearsal fills it with the served
   risk, so the two rows match by construction. A partner should drop the column or export it from a research build.
5. **Drift alerted**, as expected with no account history and against a synthetic reference
   ([PILOT_ONBOARDING.md](PILOT_ONBOARDING.md) section 9); the band rates are several times the reference.

## How to read the comparison

The labels are the stream's synthetic `y`; a case is the payee account of a labelled payment, confirmed two days
later. The "incumbent" is a stand-in that ranks by USD amount, because no real incumbent exists here; beating it says
little. The engine was trained on data from the same synthetic generator, so its lead here is expected and is not
evidence for a bank's data. The pre-registered AMLSim holdout, where it did not transfer, is the more relevant warning
([DEMO_SCRIPT.md](DEMO_SCRIPT.md), limits).
