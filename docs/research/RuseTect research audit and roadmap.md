# Engineered features, not extra stages, drive RuseTect

RuseTect's measurable detection power comes from **31 past only account history and network features inside one XGBoost model**, not from the number of layers around it. The brief's starting assumption is wrong on one point: **the first stage (L1) is an XGBoost gatekeeper, and LightGBM appears only as one half of the L2 average and in the L0 onboarding model** ([rusetect_engine.py](/home/claude/iit-delhi-raksham/service/rusetect_engine.py)). On IBM AMLworld HI-Small test weeks the live path scores **PR-AUC 0.711 and ROC-AUC 0.985**, but on LI-Small it falls to **0.345**, and the only truly out of distribution figure (models never trained on LI) is **0.336** ([full_eval_HI.json](/home/claude/iit-delhi-raksham/results/full_eval_HI.json), [retrain_extended.json](/home/claude/iit-delhi-raksham/results/retrain_extended.json)). The block band a bank would see today is **63.8% precise at 65.3% recall**, not the 91% to 97% figures the Round 1 submission quoted, which came from an offline stacker that is not served ([live_path_audit.json](/home/claude/iit-delhi-raksham/results/live_path_audit.json)). Every training source is synthetic, simulated, authored or foreign, and no public, labelled, real UPI transaction dataset exists, so the next gains come from cross generator testing (AMLworld Medium and Large, SAML-D, AMLgentex), real label sanity checks on non UPI graphs (Elliptic++, DGraph-Fin, Libra Bank), and institutional access. The literature supports adding subgraph pattern features to the trees, calibrating each model, and reporting alert budget and cost metrics; it does not support replacing the trees with a graph neural network. The project's strongest research asset is its discipline (chronological splits, train and serve parity, preregistered adoption rules, honest negative results), and the jury conversation should trade that discipline for data access and deployment constraints.

## Phase 1: two learned stages, not seven, make the payment decision

### What the code actually runs

The live payment path is a two stage cascade. **L1 is an `xgb.Booster` with 30 trees; if its score is below 0.0563 the payment is approved and exits. Otherwise L2 risk is the plain mean of an XGBoost and a LightGBM score** on the same 31 features, and the result is banded at verify 0.1366, hold 0.4495 and block 0.8230 ([rusetect_engine.py lines 76 to 149](/home/claude/iit-delhi-raksham/service/rusetect_engine.py), [cascade_config.json](/home/claude/iit-delhi-raksham/service/models/cascade_config.json)). Features are computed from account state before that state is updated with the current payment, so they are past only with respect to labels, and the training features were built by streaming through the same serving state code in time order ([RETRAINING.md](/home/claude/iit-delhi-raksham/docs/RETRAINING.md)). LightGBM is served from JSON by a pure NumPy evaluator ([README.md](/home/claude/iit-delhi-raksham/README.md)). Reason chips are TreeSHAP contributions from **the L2 XGBoost booster only**, so they explain half of a score that is an average of two models ([rusetect_engine.py lines 150 to 154](/home/claude/iit-delhi-raksham/service/rusetect_engine.py)). L4 is a deterministic union find "ring linker" over payments in the high band, not a learned model.

Around this core sit layers that are implemented and unit tested but mostly not measured on real signal: a message model (logistic regression on hashed TF-IDF with a six rule hard signal floor), lure to payment fusion, context rules, session coercion weights (screen share 0.30, paste 0.20, hesitation 0.20, SIM swap 0.15, app hidden 0.10, network 0.05, step up at 0.65), typing and mouse verifiers, campaigns, an Ed25519 signed, hash chained consortium ledger of HMAC tokens (not a blockchain), and a two analyst review desk with a template based STR draft ([SESSION_AND_NETWORK.md](/home/claude/iit-delhi-raksham/docs/SESSION_AND_NETWORK.md), [model-selection.md](/home/claude/iit-delhi-raksham/docs/model-selection.md)). The Random Forest, the L3 sequence blend, the GNN, the logistic stacker with isotonic calibration and the autoencoder novelty queue are **offline only**; the config still carries an unused `l3_sequence_weight: 0.1` ([project-audit.md](/home/claude/iit-delhi-raksham/docs/project-audit.md)). The codebase is about 7,584 lines of Python across service, scale and ml, with 53 test functions in 8 files; the tests were not run in this audit, so pass status is unverified. Calling the system a "seven layer" or "multistage ML" cascade overstates it: only two learned stages decide a payment.

### What works, what is incomplete, and where it bottlenecks

What works end to end is the payment API with the two stage cascade, streaming feature state that is bit identical in compact form on all 5,078,345 HI payments, TreeSHAP reasons, the ring linker and the review desk. What is incomplete is listed by the project's own audit: the **block threshold mismatch is open with "decision needed"**, because 0.8230 was carried over from the offline L3 blend and applied to a different live score ([project-audit.md finding 1](/home/claude/iit-delhi-raksham/docs/project-audit.md)). State lives in memory, so on Vercel a message and the next payment can land on different instances and "the fusion can silently do nothing" (finding 5). Lure to payment fusion is only unit tested because no linked message and payment pairs exist ([datasets.md](/home/claude/iit-delhi-raksham/docs/datasets.md)). There is no call audio or voice detection, session signals have no public benchmark, the docker compose path is untested, and SAML-D was proposed but never run ([SCALING.md](/home/claude/iit-delhi-raksham/docs/SCALING.md)).

Several documents are stale after the LI-Small retrain, and a jury reading them literally would be misled. `full_eval_LI.json` still says LI was "never used for training" although its 0.345 comes from the HI plus LI retrained models; SCALING.md still quotes 0.716 and 0.336 for the previous models; model-selection.md says L4 "turns 1,105 alerts into 318 cases" while checks.json says 1,140 into 349; and the config's validation traffic shares (0.13% / 0.31% / 0.50%) disagree with the audit's 0.443% hold or block and 0.945% step up or above ([full_eval_LI.json](/home/claude/iit-delhi-raksham/results/full_eval_LI.json), [checks.json](/home/claude/iit-delhi-raksham/results/checks.json)).

The architectural bottlenecks are concrete. The live score is an **uncalibrated mean** of two boosters trained with 10% negative subsampling and `scale_pos_weight`, so thresholds do not transfer between models, which is exactly how the block mismatch arose. Reasons explain only the XGBoost half, and **LightGBM is now the weaker half** (HI test 0.604 alone versus 0.711 for XGBoost) ([l2_halves_check.json](/home/claude/iit-delhi-raksham/results/l2_halves_check.json)). A missing `payment_format` defaults to "ACH" and a missing currency to US Dollar ([server.py lines 131 to 140](/home/claude/iit-delhi-raksham/service/server.py)); since payment format is a known shortcut feature (removing it drops PR-AUC from 0.728 to 0.701), an incomplete record can be scored as higher risk for an artefactual reason ([checks.json](/home/claude/iit-delhi-raksham/results/checks.json)). Finally the distributed path is two orders of magnitude slower in tail latency than the single process path, so the Redis design is a floor, not a capacity claim.

### What a banking or ML expert would attack first

An experienced reviewer would note that **no metric is confidence bounded**: there is no bootstrap, seed variance or interval anywhere, so differences such as 0.7107 versus 0.7108 or 0.725 versus 0.728 are inside unknown noise. They would note that the IBM HI-Small test covers **only 2022/09/01 to 2022/09/18 of simulated time**, so "chronological" means an 18 day horizon on one generator, and that prevalence shifts sharply inside it (1,082 laundering in validation versus 1,797 in test of equal length; validation AP 0.633 versus test 0.711) ([live_path_audit.json](/home/claude/iit-delhi-raksham/results/live_path_audit.json)). They would find that the rules challenger is degenerate, with thresholds like "sender made at least 20,550 payments in 24 h" and "amount at least $3,808,605", two of which fire on 1 and 2 test payments, so any "15x fewer alerts than rules" claim is against a straw man ([layered_engine.json](/home/claude/iit-delhi-raksham/results/layered_engine.json)). They would see there is **no cost sensitive evaluation, no amount weighted recall, no ring level precision and no payment side adversarial test**. And they would point out the context and graph checks "were designed after looking at the bundled sample", so their small gains are optimistic ([full_eval_HI.json caveats](/home/claude/iit-delhi-raksham/results/full_eval_HI.json)).

### Where the genuine research contribution lies

The publishable value is in evaluation methodology and honest negative results rather than in a new model. The repo demonstrates **train and serve parity by construction** (features identical on 5,078,345 payments; Bloom index decisions agree 100%), a **strictly causal benchmark of 14 tabular and 4 sequence models** on AMLworld with validation only selection, **preregistered adoption rules** for every swap, an **unseen typology holdout** in which XGBoost keeps 0.80 to 0.85 recall on removed typologies while Isolation Forest recovers 0.0 on all four, a BAF fairness control (bias features x1 and x2 raise ROC-AUC to 0.954 but collapse age parity to 0.185), and a PaySim shortcut diagnosis (0.52 without balances, 0.9997 with payer balance) ([scale_bench.json](/home/claude/iit-delhi-raksham/results/scale_bench.json), [baf_variant_eval.json](/home/claude/iit-delhi-raksham/results/baf_variant_eval.json), [paysim_eval.json](/home/claude/iit-delhi-raksham/results/paysim_eval.json)). The threshold transfer bug is itself a cautionary case study worth writing up.

## Phases 2 and 3: no public labelled UPI data exists, so diversity must come from elsewhere

### Real, anonymised, synthetic and simulated are four different grades of evidence

The search confirmed a hard fact the jury should hear early: **no public dataset of real UPI transactions with fraud labels exists**. The one Kaggle "UPI" set inspected in detail, UPI Transactions 2024 (250,000 rows, 480 frauds, 0.19%), is described by its own analysis repo as "a simulated (synthetic) dataset" with no confirmed payer or payee IDs ([analysis repo](https://github.com/daisymargarate1309/upi-fraud-detection-analysis)). RBI treats MuleHunter.AI outcome data as fiduciary and refused under RTI to disclose even the count of flagged mule accounts ([MediaNama](https://www.medianama.com/2025/12/223-rti-23-banks-mulehunter-mule-accounts/)). Even a 2026 study of mobile money laundering in Rwanda had to use synthetic SAML-D for lack of real data ([arXiv 2608.15447](https://arxiv.org/pdf/2608.15447)).

The candidates therefore fall into four grades, and the report keeps them separate throughout. **Real, non anonymised public records** are the public blockchains: the Ethereum phishing network and the Elliptic family's underlying Bitcoin graph. **Real, anonymised records** are DGraph-Fin (Chinese consumer lending), Libra Internet Bank (Romania), Berka PKDD99 (Czech bank), T-Finance and T-Social, ULB credit card, IEEE-CIS and the Elliptic feature sets (obfuscated features over real transactions). **Synthetic data derived from real data** includes SynthAML (real Spar Nord alerts synthesised with SDV), the RBA login dataset (synthesised from real login behaviour, "totally artificial" values), and BankSim (calibrated on aggregate Spanish bank data). **Simulated environments** with generator ground truth are AMLworld, SAML-D, AMLgentex, AMLSim, PaySim, Sparkov, TabFormer, the JPMorgan synthetic sets, LDBC FinBench and the Kaggle UPI uploads. Only simulated sets give mule style payment graphs with labels; only real sets test whether methods survive noisy, human assigned labels.

### Which additions give genuinely new information

Ranked by new information per hour of work, the order is clear. **AMLworld HI-Medium** is the cheapest step (same loader, 32M rows fit a workstation) and gives a three day test window; **HI-Large** is the only AMLworld option with enough time span (97 days) for monthly walk forward validation ([Altman et al.](https://arxiv.org/pdf/2306.16424)). **SAML-D** is the cheapest independent generator: training on IBM and testing on SAML-D (or the reverse) directly measures how much of RuseTect's 0.711 is generator artefact. **AMLgentex** is the strongest new synthetic source because Swish and Bizum are instant P2P mobile rails and each of its 12 banks sees only its local view, which mirrors how a UPI payer PSP and payee bank each see half of a mule chain ([Östman et al.](https://arxiv.org/pdf/2506.13989v2)). **RBA** and the **JPMorgan customer journey** set are the only public sources found for pre payment session behaviour, which matters because coerced, authorised scam payments often look normal at the transaction level. For real labels, Elliptic++ actors, DGraph-Fin, Libra Bank and Ethereum phishing should be used to check that ring features and any GNN arm survive noisy human labels, not as production training data. Card benchmarks largely duplicate BAF and PaySim style supervision; keep at most TabFormer or Sparkov for sequence pretraining and IEEE-CIS for device features. **No public dataset labels "mule accounts" explicitly**; mule labels must be derived (for example accounts on laundering paths with fan in then rapid fan out), following the CFDB customer aggregation method ([arXiv 2404.14746](https://arxiv.org/pdf/2404.14746)), whose per customer counts for HI and LI-Small appear swapped relative to IBM's table and should be recomputed.

For UPI realism, the public anchors are aggregates. UPI handled **25.47 billion transactions worth Rs 31.53 lakh crore in October 2026, about 822 million per day** ([Free Press Journal](https://www.freepressjournal.in/business/upi-transactions-hit-2547-billion-in-october-value-soars-to-3153-lakh-crore)). I4C/NCRP data, via secondary reporting, puts 2025 citizen losses at **Rs 19,812.96 crore across 21,77,524 complaints, with investment scams 77% of losses and digital arrest 8%** ([FastBull citing I4C](https://www.fastbull.com/brokersview/news/indians-lost-over-%E2%82%B9198-billion-to-financial-fraud-in-2025-i4c-ncrp-data-show-319040)). RBI's own fraud tables cover only frauds of Rs 1 lakh and above and show an implausible FY26 card and digital figure (293 cases, Rs 29 crore, against 13,332 cases in FY25), which looks like a reporting or classification change, so they should not size UPI scams ([Outlook Business / PTI](https://www.outlookbusiness.com/news/financial-institutions-report-over-10000-cases-of-fraud-involving-48000-cr-in-fy26-rbi-data)). A rough complaint rate of about 1 in 100,000 UPI transactions follows from these aggregates; this is an estimate, since complaints are not transactions. A UPI style simulator recalibrated on these aggregates (AMLSim or AMLgentex with single currency, account to account instant transfers, VPA and device fields) is the realistic route to "UPI data" without a partner.

## Phase 4: graph features in trees beat graph networks under causal evaluation

The literature lines up with RuseTect's own negative results. On AMLworld, **FraudGT reports minority class F1 of 76.13 on HI-Small against 63.23 for XGBoost with graph features and 68.19 for Multi-PNA**, but the GNN advantage is not uniform (Multi-PNA collapses to 6.59 on Large-LI against 24.23 for XGBoost with graph features), the metric is F1 at a tuned threshold rather than PR-AUC, and message passing inside an evaluation window is not strictly past only per decision ([FraudGT](https://jshun.csail.mit.edu/FraudGT.pdf)). When future graph context is removed, the picture flips: an April 2026 strict inductive reevaluation on Elliptic found **Random Forest F1 0.821 and XGBoost 0.775 beat GraphSAGE 0.688, GAT 0.610 and GCN 0.503**, transductive versus inductive GraphSAGE differed by 39.5 F1 points, and shuffled edges scored higher than the real graph ([Maganti, arXiv 2604.19514](https://arxiv.org/html/2604.19514)). RuseTect's causal GNN at 0.516 against XGBoost at 0.72 fits that pattern. The best supported graph upgrade is the **Graph Feature Preprocessor**: past only fan in, fan out, scatter gather, gather scatter, simple and temporal cycle counts and windowed vertex statistics fed to boosted trees, reporting up to 36% minority class F1 improvement over GNN baselines and higher throughput on a 32 core CPU than GNNs on a V100 GPU ([Blanuša et al., ICAIF 2024](https://arxiv.org/html/2402.08593v2)).

Mapped onto the brief's eight questions, the evidence gives specific answers. Graph based account relationship analysis is worth it **as features**, not as a model. Temporal behaviour modelling is already the largest single gain (sender behaviour lifted PR-AUC from 0.180 to 0.540), so its next step is longer windows on HI-Large, not a new network. Velocity and sequence analysis should enter as GFP windowed statistics and at most one fused embedding. Unsupervised anomaly detection should be demoted to monitoring, since the autoencoder added only 25 catches for 507 alerts and Isolation Forest added none ([postanalysis.json](/home/claude/iit-delhi-raksham/results/postanalysis.json)). Risk based prioritisation needs alert budgets and a capacity aware review band. Multi account correlation should move from "shared account in blocked payments" to "shared flow pattern" via scatter gather and short cycle counts around flagged accounts, with ring level precision reported.

### What the metrics mean at UPI scale

The headline ROC-AUC of 0.985 is the least informative number in the repo, because at 0.177% prevalence a model can have near perfect ROC-AUC while nine of ten alerts are false. PR-AUC and operating points are the right lens, and they expose two problems. First, **calibration**: the only calibrated scores in the repo (Brier 0.00076, ECE 0.00025) belong to the offline stacker, and the live score has no calibration at all ([layered_engine.json](/home/claude/iit-delhi-raksham/results/layered_engine.json)). Second, **prevalence**: HI-Small has one laundering payment per 565, while the I4C aggregates suggest roughly one complaint per 100,000 UPI transactions. If the block band kept the same detection and false positive rates at that prevalence, its precision would fall from 0.638 to roughly 1%, and even the retuned threshold would reach only about 8% (derived, rough, assuming unchanged rates). At 822 million UPI payments per day, a 1.5% verify rate would mean about 11 million step ups per day, and the average load alone is about 9,500 payments per second, ten times the Redis scale out measurement. These derived figures are illustrations, but they are the arithmetic a banking juror will do in their head, and RuseTect should do it first.

Per category performance is reported only by AMLworld typology (BIPARTITE weakest at 0.762 ring recall at block) and by message workflow (family emergency 0.50, parcel customs 0.582). No amount weighted recall exists, so it is unknown whether high value laundering is caught preferentially, and no cost model sets the price of a missed mule credit against a false hold on a genuine customer.

### Random versus chronological validation

No random split comparison exists: searches for `train_test_split`, `StratifiedKFold` and `shuffle=True` in ml/ return nothing, and every payment result is chronological. That is a strength, not a gap in rigour, but it leaves the most persuasive slide unmade. Running the same pipeline with a shuffled split would quantify how much a typical random split benchmark overstates performance on AMLworld, and the Elliptic reevaluation's 39.5 point transductive versus inductive gap suggests the effect can be large ([Maganti](https://arxiv.org/html/2604.19514)). It is a one day experiment and should be in the deck.

If the interaction allows only five questions, ask **1, 4, 6, 14 and 16**, in that order. Question 1 attacks the single largest weakness (all data synthetic) and is the only one that could change the project's trajectory. Question 16 is the concrete, low risk ask that turns interest into a pilot. Questions 2 and 7 are the best substitutes if the panel includes RBIH or a bank risk officer respectively.

## Conclusion

The most important change in understanding is that RuseTect is not a multistage detector that needs more stages; it is a well engineered single model whose features carry the signal, wrapped in layers that are designed for data the project does not yet have. That reframing is a strength in front of an expert jury: the team can show that it measured each layer, kept what helped and dropped what did not, which is rarer than a high headline number. The weakness a juror will find in minutes is not the model but the gap between the evidence and the claims, so the submission materials must be brought into line with the repo before the finale.

The practical implication is that the next large gain will not come from architecture. It will come from three things only outsiders can provide or force: real or realistically calibrated data with real label definitions and delays, an operational target (alert budget, cost ratio, latency budget) that defines what "good" means, and a second generator or real label set that tests whether 0.711 survives outside IBM's simulator. The 20 questions and the Level 1 roadmap are designed so that every conversation with the jury either produces one of those three things or produces a result that makes the project more publishable without them.
